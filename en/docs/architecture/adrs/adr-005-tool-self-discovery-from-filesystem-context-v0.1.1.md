# ADR-005: Tool Self-Discovery from Filesystem Context

```yaml

date: 2026-05-10
amended: 2026-07-09 (resolved artifact path; fallback rule; cache ordering; see Amendments)
version: 0.1.1
```

## Context

SAT tools currently assume an operational language context — they are in `en/bin/` but do not derive any behaviour from that location. The language-as-archive-root model (ADR-001) applies to content archives but has not been extended to the tool itself. This means the tool's own operational context is undeclared, and archives created by the tool do not automatically inherit a language default derived from the tool's own structural position.

A secondary problem exists in the validation pipeline. ADR-003 establishes the IANA Language Subtag Registry as the authoritative source for language directory name validation but defers the question of how that registry is accessed, cached, and used when offline. This leaves a gap between the decision and the implementation.

Two tool configuration concerns have been conflated with archive configuration concerns: how SAT validates language expressions, and what defaults SAT applies when creating archives. These are tool responsibilities, not archive responsibilities. They belong in tool configuration space, not in any archive directory.

Since this record was first drafted, tool distribution has moved to a system-installed, wrapper-resolved model: `osat-fluent-sat-tool` places versioned artifacts under `~/.local/share/sat-tool/<version>/` and generates operator wrappers in `~/.local/bin/`. Instances reach the tools through symlinks and wrappers rather than embedded copies. Discovery must be defined against that indirection.

## Decision

### 1. Tool self-discovery

When a SAT tool executes, it determines its own operational language context by reading its position in the filesystem. The tool walks upward from its own location to find the nearest language archive root — the first ancestor directory whose name is a valid BCP 47 language tag or mixed-language tag as defined by ADR-001 and ADR-002.

**Discovery operates on the resolved artifact path.** Symlinks — the operator's wrapper, delegated instance bin tiers — are resolved before the walk begins. The walk therefore runs inside the language-structured installed artifact (`$SAT_TOOL_ROOT/en/bin/...`), never inside an instance's symlink farm, and a tool invoked from any delegated location discovers the same context as the artifact it resolves to.

**The pattern test is registry-backed, not structural.** Structural plausibility is insufficient: `bin` and `sat` are both well-formed primary subtags in shape, and a structural walk from `en/bin/sat/sat` would stop at `sat/` and answer wrongly. Each ancestor is validated against the IANA registry cache; a directory name that fails validation — unregistered, non-canonical casing, wrong mixed ordering — is not a language archive root and the walk continues. A consequence for sequencing: the walk itself needs no external state, but its validation depends on registry cache resolution having completed. Well-formed private use tags (`x-humpback-songs`) are valid BCP 47 and do match, so previously generated non-authority archive roots are discoverable with no special cases.

The discovered language context becomes the operational default for that tool invocation. Archives created by the tool inherit this default unless overridden at the collection, archive, or document level through the cascade defined in the SAT Filesystem and Configuration Cascade Specification v0.0.2.

```text
~/.local/bin/sat (wrapper)
  ↓ resolves to
$SAT_TOOL_ROOT/en/bin/sat/sat executes
  ↓
tool walks upward: bin/ → en/
  ↓
en/ validates against the IANA registry cache
  ↓
operational language context: en
  ↓
dc:language: eng, dc:language_bcp47: en, sat:authority: external
```

**Non-authority fallback.** When no ancestor matches before the filesystem root, the non-authority model of Language in SAT: A Structural Approach v0.0.5 section 9 applies. The fallback candidate name is the nearest ancestor directly above the innermost `bin/` tier — `humpback_songs` for a tool at `humpback_songs/bin/content/`. When no `bin/` tier exists on the path, no fallback name is guessed and the caller must supply the expression explicitly. A private use `x-` prefixed BCP 47 tag is generated from the fallback name, `sat:authority: none` is declared, and an authority note is written. The tool does not fail.

### 2. Separation of tool configuration from archive configuration

Tool configuration — validation rules, registry cache location, staleness policy, default behaviour flags — lives in `~/.config/sat/` on the operator's machine. It is never inside any archive directory. It is generated by the tool on first run and owned by the operator thereafter. The tool never overwrites operator configuration without explicit instruction.

Archive configuration — what a specific archive is, its language, rights, creator — is generated at archive creation time from the tool's discovered context and the cascade. It lives inside the archive. Once written it belongs to the archive, not to the tool.

### 3. Archive immutability by default

Once an archive is created its language declaration is a fact of record. The IANA registry consulted at creation, the `sat:authority` declared, and the `dc:language` written to the archive's assets records are the authoritative record for that archive at that point in time. The tool never overwrites these records automatically.

If the IANA registry adds an entry for a previously `sat:authority: none` expression, the tool detects this on next validation run and offers an upgrade. The operator decides. The tool proposes, never imposes.

## Alternatives Considered

**Hardcode `en` as the tool default** — rejected because it embeds an English assumption invisibly, exactly the failure mode SAT was designed to avoid.

**Require explicit language flag at invocation** — rejected because it creates friction for the common case and does not scale across tool invocations in automated pipelines.

**Derive language from a configuration file rather than filesystem** — rejected because it duplicates information already present in the filesystem structure, creating a second source of truth that can diverge.

**Place registry cache inside the SAT installation directory** — rejected because it mixes tool state with tool code, making upgrades destructive to cached data.

**Structural-only pattern test (no registry lookup during the walk)** — rejected because ordinary directory names (`bin`, `sat`, `lib`) are structurally valid primary subtags and the walk would terminate on them incorrectly.

**Walking the invocation path rather than the resolved path** — rejected because delegated symlinks and the operator wrapper would make the discovered context depend on where the tool was invoked from rather than what the tool is, and instance bin directories are not language archive roots.

## Consequences

- The tool's own directory name is a language declaration, not a convention
- SAT ships in `en/` — English is the default not because it was assumed but because it was declared structurally
- New language editions of SAT (`fr/`, `fr-CA/`, `ase/`) automatically operate in their declared language context without code changes
- Tool configuration is cleanly separated from archive configuration
- Created archives carry their own provenance independent of the tool's current cache state
- Offline operation is supported without degrading the authority model
- Non-human language archives (`humpback_songs/`) are handled with the same mechanism as registered human languages — no special cases
- Discovery is deterministic under delegation: every symlink path to the same artifact discovers the same context
- Implemented in `satlib/discovery.py`; the walk examples of the validation specification section 1.2 are its test cases
